## 1. 무엇을 바꿨나

### 기존 (CPU first-fit)

- net을 우선순위(hpwl 내림차순)로 훑으며 "충돌 없는 첫 batch"에 배정
- 완전 순차 → GPU 유휴, 큰 디자인에서 30초 소요

```
for net in priority order:
    for batch in 0, 1, 2, ...:
        if net.points 가 batch map에 안 걸리면: 이 batch에 넣고 종료
```

### 논문 (InstantGR journal, TCAD 2026, Sec. III-D)

- *GPU-Accelerated Batch Generation* — batch를 하나씩 만들면서 남은 net **전부**를 병렬 처리
- **commit** : 각 net이 자기 mark를 batch map에 `atomicMin`으로 기록 → 우선순위가 높은(인덱스가 작은) net이 셀을 선점
- **check** : 자기 point를 전부 자기가 소유한 net을 그 batch에 배정
- **rule out** : 이미 배정된 net에 막힌 net은 이번 batch를 포기, 자기 mark는 회수
- 더 배정할 net이 없을 때까지 반복 → 다음 batch
- 논문 보고치 : CPU 대비 약 3배 (Table II, 벤치 10–13)

### 실제로 채택한 구조

- 논문의 **중재(commit-check + `atomicMin` 우선순위)는 유지**, **스케줄링만** CPU first-fit 구조로 회귀 (이유는 3절)
- **window** : batch 여러 개를 동시에 열어두고 bitmap 유지 → 새 batch뿐 아니라 예전 batch에도 들어갈 수 있음
- **wavefront** : 우선순위 앞쪽 일부(수백~수만 net)만 in-flight. 배정 수에 맞춰 매 라운드 자동 조절
- **pick** : 각 net이 자기가 멈춘 지점부터 열린 batch를 스캔해 point가 비어 있는 첫 batch 선택. 막힌 batch는 계속 막히므로 되돌아가지 않음 → **실패가 bitmap 읽기 몇 번, commit 없음**
- **commit / check** : 고른 batch 하나에만 라운드당 1회
- **net당 warp(32 레인)** : 레인이 batch 32개를 동시에 테스트(`__ballot_sync`)하고, mark·point도 나눠서 처리

기하·판정은 CPU 경로와 동일 :

- mark : h/v RSMT segment + point 주변 4셀 십자(`mark_3x3`)
- 충돌 판정 : 자기 **point만** 검사
- 불변식 : batch 안에서 어떤 net의 point도 자기보다 앞선 멤버의 mark에 덮이지 않음

## 3. 과정 — 논문 그대로는 왜 더 느렸나

| 시도 | S1 batch gen | S2 batch gen | 문제 |
| --- | --- | --- | --- |
| CPU first-fit (기준) | 3.15s | 3.50s | — |
| 1차 : 논문 스케줄링 그대로 | 5.51s | 12.93s | net당 commit 수백 회 |
| 2차 : window + wavefront | 3.44s | 13.41s | 진 net이 wavefront에 남아 안 줄어듦 |
| 3차 : 라운드 오버헤드 제거 | 3.62s | 13.68s | 라운드당 4.9ms — 커널 내부 문제 |
| 4차 : net당 warp | 0.95s | 1.67s | wavefront 하한이 커밋 낭비 |
| 5차 : ring·wavefront 튜닝 | **0.80s** | **1.18s** | — |

- 위 표는 `mempool_group` 기준

**1차 — 논문 스케줄링**

- batch를 하나씩 채우면 net 하나가 "자기가 최종적으로 들어갈 batch 번호"만큼 full commit 반복
- S2 : net 197k에 batch 869개 → net당 평균 430회, 여기에 batch당 commit-check 라운드 5.1회가 곱해짐
- CPU가 빠른 이유는 **실패가 싸기** 때문 — `has_conflict`는 point 몇 개 읽고 첫 충돌에서 리턴
- 논문 알고리즘은 실패 1회 비용을 100배로 키운 셈

**2차 — window + wavefront**

- 실패는 싸졌으나 진 net이 계속 in-flight로 남아 wavefront가 안 줄어듦
- 미배치 리스트 앞부분을 wavefront로 쓰는 구조로 변경해 해결

**3차 — 라운드 오버헤드**

- `thrust::copy_if`가 호출마다 임시 버퍼를 `cudaMalloc`/`cudaFree`, `cudaFree`는 디바이스 전체를 동기화
- compaction을 호스트로 이전하고 thrust 의존 제거 → 시간은 그대로
- 원인은 커널 내부였음

**4차 — net당 warp (결정적)**

- 모든 커널이 net당 스레드 1개
- wavefront 1024 → 스레드 32워프뿐, TITAN RTX는 SM만 72개라 지연 은닉 불가
- pick : net 하나가 열린 batch 871개를 **순차 의존 체인**으로 훑음
- commit/check/release : augmented DAG net은 mark가 수백~수천 개인데 스레드 하나가 다 순회
- 레인 32개로 분할 → S2 13.68s → 1.67s

**5차 — 큰 디자인**

- `mempool_cluster_ranking`의 S2만 이득 없음 (14.23 vs 14.56), 로그에 원인 노출
- `retired 101` : grid 20.6M 셀 → bitmap 하나가 2.58MB, 1GB 예산이면 ring이 374개인데 batch는 474개 필요 → 조기에 닫은 batch만큼 batch 수가 늘어(474 vs 461) S2 GPU route가 +1.36s → **예산 2GB**
- `16.8 commits per net` : wavefront 하한 1024인데 라운드당 배정이 62개 → 커밋의 94%가 헛일. 하한 1024는 net당 스레드 1개였을 때 값 → **하한 256** (net당 warp면 256 net = 8k 스레드)
- 하한 인하 효과는 `mempool_group`에도 반영 — S2 `commits per net` 13.9 → 5.1, 시간 1.67s → 1.18s

## 4. CPU 경로와 다른 점

- 논문의 rule-out은 **배정된 net 전체**와 비교, CPU first-fit은 **자기보다 앞선 net**과만 비교 → 우선순위가 낮은 net이 먼저 배정되면 그보다 높은 net이 다음 batch로 밀릴 수 있음
- 라운드 안에서 서로 다른 batch를 고른 net이 같은 셀을 놓고 경쟁하면 진 쪽은 다음 라운드에 재시도 (owner map을 batch마다 두지 않기 위한 의도적 타협)
- 결과적으로 net별 배치는 상당수 달라지지만 **batch 수는 거의 동일** (383=383, 460 vs 461, 603 vs 601)

## 5. 검증

- **호스트 시뮬레이션** : 커널을 CPU에서 순차 실행(`kPickLanes=1`)해 무작위 net 최대 60k로 검사 — 모든 net이 정확히 한 batch에 배정 · batch 내 충돌 없음 · 상한 준수 · 재실행 시 동일 결과 · batch 수가 CPU first-fit과 일치(18/18, 152/152, 135/135)
- **실기** : `INSTANTGR_GPU_BATCH_GEN_VALIDATE=1` → `conflict-free: yes`, CPU 결과와 batch 수·이동 net 수 비교 출력
- **컴파일** : GitHub Actions에서 nvcc 12.5 / sm_75 · sm_86
- **폴백** : GPU 메모리 부족 등 실패 시 경고를 찍고 CPU 경로로 자동 복귀
