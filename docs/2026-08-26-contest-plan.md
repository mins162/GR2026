## 3. 서사 — 창의성 30% 공략

### 3-1. 첫 페이지 프레이밍

"라우터를 2배 빠르게 했다"(X) → **"설계 반복을 2배로 만들었다"**(O)

> 칩 하나를 설계할 때 라우팅은 P&R 시간의 상당 부분을 차지하고, 설계 반복 한 번의 대기 시간을 결정한다.
> 우리는 이 단계를 GPU로 가속해 **설계자가 하루에 돌릴 수 있는 반복 횟수를 2배로** 만들었다. 배선 품질 손실은 0이다.

심사위원이 **반도체 설계자의 언어로** 이해할 수 있어야 한다.

### 3-2. 핵심 서사 — "논문을 따라한 게 아니라 반증하고 이겼다"

대부분의 학부 보고서는 "이거 했고 몇 % 빨라졌습니다" 나열이다. 우리는 다른 걸 갖고 있다 :

> TCAD 2026 저널판이 기여로 내세운 GPU batch generation(§III-D)을 **그대로 구현했더니 CPU보다 3.7배 느렸다** (S2 3.50s → 12.93s).
> 원인을 분석하니, net 하나가 자기 최종 batch 번호만큼 full commit을 반복해 net당 **~430회**였다.
> CPU가 빠른 진짜 이유는 병렬성이 아니라 **실패가 싸기** 때문이었다 (`has_conflict`가 첫 충돌에서 즉시 리턴).
> → 논문의 우선순위 중재(atomicMin)는 살리고 **스케줄링만 버려서**, 실패를 싸게 만드는 window/wavefront 구조로 재설계.
> → net당 warp로 pick 의존 체인을 1/32로 단축.
> → **S2 12.93s → 1.18s.**

- 이건 "논문을 읽고 따라했다"가 아니라 **"최신 SOTA 논문을 실측으로 반증하고 이겼다"**이다.
- 지금 `docs/` 어디에도 "우리가 논문보다 낫다"는 말이 없다. 전부 겸손하게 "구현했다"로 쓰여 있다. **보고서에서는 명확히 주장할 것.**

### 3-3. 두 번째 서사 — 하나의 원리

> 관찰 : batch 하나가 건드리는 grid는 **P50 기준 1.2%**. 그런데 baseline은 매 batch마다 100%를 재계산한다.
> 원리 : GPU 라우터의 병목은 병렬화 부족이 아니라 **"변경분 대비 재계산량의 비대칭"**이다.

- 이 원리로 얻은 것이 전체 절감분의 **58%** (`update_cost` −99.1%, `compute_presum` −76.8%)
- 이건 **저널 논문 기여 5개 어디에도 없는 우리 고유 아이디어**다 (`archive/2026-08-25-journal-gap.md` 대조 완료)

### 3-4. 세 번째 서사 — 실패도 결과다

- tree-center : depth를 평균 **23% 줄였는데 runtime은 안 줄었다** → critical path가 지배한다는 걸 밝히고 → leaf peeling으로 호스트 비용을 낮춰 순이득 전환
- batch gen 1차 실패 → 5차까지의 재설계 기록
- 파이프라인 : **하지 않기로 판단한 근거**를 정량으로 제시 (이득 상한 6%, 판정 기준 미달)

→ 학부 보고서에서 **판단 근거를 정량으로 제시하고 "안 한다"를 결론으로 쓰는 팀은 거의 없다.** 완성도 40%에 직결.

### 3-5. 네 번째 서사 — 오버랩은 자원이 다를 때만 공짜다

**보고서에서 채택(FLUTE 오버랩)과 기각(batch gen 파이프라인)을 같은 원리로 묶는다.** 이렇게 하지 않으면 "오버랩이 우리 핵심 기여"와 "파이프라인은 안 했다"(§6)가 서로 모순으로 읽힌다.

> **오버랩의 이득은 겹치는 두 작업이 서로 다른 자원을 쓸 때만 나온다.**
>
> - **FLUTE 오버랩 — CPU 루프 ∥ GPU 커널 (다른 자원)** → 이득 그대로. cluster에서 RSMT −17.4s, GPU wall 9.39s가 CPU 뒤로 통째로 숨음 (`tail beyond CPU loop = 0.000s`). **채택**
> - **batch gen ∥ route — GPU ∥ GPU (같은 SM 경쟁)** → 총합이 `max(gen, route)`로 바닥이 막힘. 실측 gen 12.93s > route 5.73s라 이득이 음수. **기각**
>
> 우리는 두 경우를 **모두 구현·측정**한 뒤 하나를 채택하고 하나를 기각했다.

- 근거 문서 : `2026-08-25-pipeline-plan.md` ("겹치는 두 쪽이 CPU↔GPU면 이득이 크고, GPU↔GPU면 유휴율부터 확인")
- 심사 관점 : "오버랩 했습니다"보다 **"오버랩이 언제 통하는지 알아냈습니다"**가 훨씬 강하다. 기각 판단이 같은 원리에서 나오면 §6이 자동으로 정당화된다

### 4-2. 우리 기여 — 큰 순서

절감 크기(`archive/2026-08-23-best-result.md` §3 귀속표)와 독창성을 함께 본 순위. **보고서 방법 절도 이 순서로 쓴다.**

| 순위 | 기여 | 절감 (group / cluster) | 독창성 | 근거 |

| **2** | **CPU/GPU 오버랩 스케줄링** | **−0.02s ⚠ / −17.4s** | ★★★ | ICCAD'22 논문에 없음. **cluster에서 GPU가 통째로 숨음** |

- 2번과 4번은 종전에 "GPU-FLUTE −7.57s / −34.16s" 한 덩어리였던 것을 **분리한 것**이다. 분리해야 하는 이유 : 그 덩어리의 **거의 절반(cluster −17.4s)이 논문 알고리즘이 아니라 우리 스케줄링**인데, 합쳐 놓으면 통째로 "논문 재구현"으로 읽힌다.
- **순위가 절감 크기 순서와 다른 이유** — 4번은 절감이 크지만 알고리즘 자체가 남의 것이라 창의성 점수가 안 나온다. 3번은 절감이 3위지만 **SOTA 논문을 반증하고 이긴 유일한 항목**이다. 심사 배점(창의성 30%) 기준으로는 이 순서가 맞다.
- ⚠ **2번 group 수치는 제출 전 반드시 재측정** — §7 참조.

#### 1위 — incremental vcost / presum

- **압도적 1위. 절감 크기도 1위, 독창성도 1위.** 이것 하나가 전체 절감의 절반 이상
- 관찰 : batch가 건드리는 grid는 P50 **1.2%** (cells) — 그런데 baseline은 매번 100% 재계산
- 구현 : ripup/commit이 `dirty_cells`·`track_dirty` 기록 → `update_vcost_selective`가 dirty + 방향 이웃 1칸만 재계산, presum은 track 단위 skip, dirty > 20%면 full rebuild로 폴백
- 결과 : `update_cost` **−99.1%** (9.98s → 0.09s), `compute_presum` −76.8%
- 검증 : nsys(CUPTI) 재측정으로 호스트 타이머와 3.5% 이내 일치 확인
- 예상보다 잘 나온 이유까지 규명함 : 커버리지는 **읽는 영역(bbox)**, skip 조건은 **직전 batch가 쓴 영역** → dirty stamp ≪ 읽기 영역
- → 그림 **V6**

#### 2위 — CPU/GPU 오버랩 스케줄링

- **ICCAD'22 논문에 없는 우리 스케줄링.** 종전에 GPU-FLUTE 덩어리에 묻혀 있던 것을 분리
- 구조 : degree ≥ 10 net은 GPU 커널로, degree < 10 net은 CPU 루프로 **동시에** 처리
- 결과 (`mempool_cluster_ranking`) : RSMT 38.09s → **20.72s (−64.6%)**. GPU wall 9.39s가 CPU 루프 뒤로 **완전히 숨음** — `tail beyond CPU loop = 0.000s`
- **원리로 승격시킬 것 (§3-5) : 오버랩은 자원이 다를 때만 공짜다**
- → 그림 **V3**. 표로는 절대 전달 안 되는 유일한 기여 — 간트 차트로 GPU 레인이 CPU 레인 밑에 숨는 모습

#### 3위 — GPU batch generation 재설계

- **창의성 30%의 핵심.** 절감 크기는 3위지만 서사 값어치는 1위
- 논문대로 1차 구현 → **CPU보다 3.7배 느림** (S2 3.50s → 12.93s)
- 원인 규명 : net당 full commit ~430회. CPU가 빠른 건 병렬성이 아니라 **실패가 싸서**
- 재설계 : 논문의 atomicMin 우선순위 중재는 유지, **스케줄링만 폐기** → window/wavefront
- 3차 : `thrust::copy_if`의 `cudaMalloc/cudaFree`가 라운드당 4.9ms를 먹는 걸 찾아 호스트 compaction으로 제거
- 4차 : net당 스레드 1개 → **net당 warp** (pick 의존 체인 1/32, `__ballot_sync`)
- 결과 : S2 **12.93s → 1.18s**, batch 수는 CPU first-fit과 사실상 동일 (품질 무손실)
- 검증 : 호스트 시뮬레이션(60k net) + 실기 `VALIDATE=1` conflict-free
- → 그림 **V5**

#### 4위 — GPU-FLUTE 알고리즘 도입

- **알고리즘 자체는 ICCAD'22 논문 것.** 절감(−6.4s / −20.5s)은 크지만 **창의성으로 주장하면 안 되고 reference 필수**
- 우리 것으로 주장 가능한 부분 하나 : **break score O(1) precompute** — 원래의 storage-free 재계산은 candidate당 O(d²)라 2153-pin net에서 ~100s로 붕괴. precompute로 해결하면서 **스코어가 bit-identical**(트리 동일)임을 증명
- 스케줄링(오버랩)은 2위 항목으로 분리했음

#### 5위 — tree-center + leaf peeling

- 절감은 작지만 **"실패도 결과다" 서사의 주인공**
- 이중 BFS tree-center로 DAG depth 평균 **−23%** (max 45 → 28) → 그런데 **runtime은 안 줄어듦**
- 원인 규명 : 평균 depth가 아니라 **critical path**가 지배 + 호스트 측 center-find 비용이 이득을 상쇄
- 해결 : 이중 BFS → **leaf peeling**으로 호스트 비용 절감 → 순이득 전환, **기본 on**
- 현재 프로파일 : S1 eligible 126,006 / center-find 0.145s, S2 eligible 81,968 / 0.058s
