데이터는 전부 이미 있다. 새 실험 없이 만들 수 있는 것들.

### 참고 — `.out` 포맷 (ISPD 2024 GR)

`src/graph.hpp:392` `output_nets()` 기준 :

```
<net name>
(
x0 y0 l0 x1 y1 l1      ← wire segment 또는 via (l0 != l1)
...
)
```

- 좌표 인코딩 : `pos / Y % X` = x, `pos % Y` = y, `pos / X / Y` = layer
- 즉 **파싱만 하면 전부 렌더링 가능**. 별도 계측 불필요.

### 3-2. 우리 기여 — 큰 순서

**수치 기준 : [rtx3060-ab.md](rtx3060-ab.md) §2 leave-one-out** (RTX 3060, 60런). 이전 TITAN 기준 수치는 폐기.
절감 크기와 독창성을 함께 본 순위 — **보고서 3장도 이 순서로 쓴다.**

| 순위 | 기여 | 마진 `group` | 비중 | 마진 `bsg_chip` | 독창성 | 근거 |
| ---: | --- | ---: | ---: | ---: | :---: | --- |
| **1** | **incremental vcost / presum** | **+47.08s** | **73.3%** | +8.72s | ★★★ | 저널 기여 5개 어디에도 없음 |
| **2** | **incremental wire-demand commit** | **+6.89s** | 10.7% | +1.10s | ★★★ | **1번과 같은 원리의 두 번째 적용** |
| **3** | **GPU batch generation 재설계** | +4.14s | 6.4% | **−0.02s** | ★★★ | 논문 §III-D 대비 재설계. 창의성 서사 최고값 |
| **4** | **CPU/GPU 오버랩 스케줄링** | +1.90s | 3.0% | +1.01s | ★★★ | ICCAD'22 논문에 없는 우리 스케줄링. **GPU가 CPU 뒤로 완전히 숨음** |
| 5 | GPU-FLUTE **알고리즘 도입** | +5.58s | 8.7% | +1.80s | ☆ | **ICCAD'22 논문 것 — 창의성 주장 금지, reference 필수** |
| 6 | tree-center + leaf peeling | +0.55s | 0.9% | +0.25s | ★★ | 우리 아이디어, 순이득 전환 |

- 1+2 = **절감의 84%가 원리 하나**. 이게 보고서 창의성 절의 뼈대다
- 4번과 5번은 종전에 "GPU-FLUTE" 한 덩어리였던 것을 **분리한 것**이다. 분리 근거 : `loo-flt`(+7.48s)에서 `loo-ovl`(+1.90s)을 빼야 알고리즘 몫(+5.58s)이 남는다. 합쳐 놓으면 **우리 스케줄링까지 통째로 "논문 재구현"으로 읽힌다**
- **순위가 절감 크기 순서와 다른 이유** — 5번은 절감이 3번째로 크지만 알고리즘 자체가 남의 것이라 창의성 점수가 안 나온다. 3번은 절감이 작지만 서사 값어치가 가장 크다. 배점(창의성 30%) 기준으로는 이 순서가 맞다
- ⚠ **3번은 `bsg_chip`에서 이득 0(−0.02s, 런 간 폭 안)** — 숨기지 말고 **"이득 조건을 정량화했다"**로 쓸 것. batch generation이 wall에서 차지하는 비중이 큰 디자인에서만 이득이 난다(`group` base 기준 6.7%)

#### 1위 — incremental vcost / presum

- **압도적 1위. 절감 크기도 1위, 독창성도 1위.** 이것 하나가 전체 절감의 **73.3%**
- 관찰 : batch가 건드리는 grid는 P50 **1.2%** (cells) — 그런데 baseline은 매번 100% 재계산
- 구현 : ripup/commit이 `dirty_cells`·`track_dirty` 기록 → `update_vcost_selective`가 dirty + 방향 이웃 1칸만 재계산, presum은 track 단위 skip, dirty > 20%면 full rebuild로 폴백
- 결과 : `update_cost` **−99.1%** (9.98s → 0.09s), `compute_presum` −76.8%
- 검증 : nsys(CUPTI) 재측정으로 호스트 타이머와 3.5% 이내 일치 확인
- 예상보다 잘 나온 이유까지 규명함 : 커버리지는 **읽는 영역(bbox)**, skip 조건은 **직전 batch가 쓴 영역** → dirty stamp ≪ 읽기 영역
- → 그림 없음 (V6은 지면 부족으로 기각, "P50 1.2%" 한 줄로 대체)

#### 2위 — incremental wire-demand commit

- **1번과 같은 원리, 다른 적용처.** 따로 세지 말고 **1번과 한 묶음으로 서술**할 것
- 결과 : `mempool_group` +6.89s (10.7%) / `bsg_chip` +1.10s (8.5%)
- 이게 있어야 "원리 하나가 절감의 84%"라는 문장이 성립한다

#### 3위 — GPU batch generation 재설계

- **창의성 30%의 핵심.** 절감 크기는 3위지만 서사 값어치는 1위
- 논문 기술대로 1차 구현 → **CPU보다 3.7배 느림** (S2 3.50s → 12.93s)
- 원인 규명 : net당 full commit ~430회. CPU가 빠른 건 병렬성이 아니라 **실패가 싸서**
- 재설계 : 논문의 atomicMin 우선순위 중재는 유지, **스케줄링만 폐기** → window/wavefront
- 3차 : `thrust::copy_if`의 `cudaMalloc/cudaFree`가 라운드당 4.9ms를 먹는 걸 찾아 호스트 compaction으로 제거
- 4차 : net당 스레드 1개 → **net당 warp** (pick 의존 체인 1/32, `__ballot_sync`)
- 결과 : S2 **12.93s → 1.18s**, batch 수는 CPU first-fit과 사실상 동일 (품질 무손실)
- 검증 : 호스트 시뮬레이션(60k net) + 실기 `VALIDATE=1` conflict-free
- ⚠ **`bsg_chip`에서는 이득 0** — 디자인 의존성을 정량화한 것으로 서술
- → 그림 **V5** (자리가 남으면)

#### 4위 — CPU/GPU 오버랩 스케줄링

- **ICCAD'22 논문에 없는 우리 스케줄링.** 종전에 GPU-FLUTE 덩어리에 묻혀 있던 것을 분리
- 구조 : degree ≥ 10 net은 GPU 커널로, degree < 10 net은 CPU 루프로 **동시에** 처리
- 결과 : S1 RSMT `group` 7.23s → **5.16s**, `bsg_chip` 2.71s → **1.61s**. GPU wall 2.20s가 CPU 루프 뒤로 **완전히 숨음** — `tail beyond CPU loop = 0.000s`
  (`mempool_cluster_ranking`, TITAN : RSMT 38.09s → 20.72s, −64.6%)
- → 그림 **V3**. 표로는 절대 전달 안 되는 유일한 기여 — 간트 차트로 GPU 레인이 CPU 레인 밑에 숨는 모습

#### 5위 — GPU-FLUTE 알고리즘 도입

- **알고리즘 자체는 ICCAD'22 논문 것.** 절감(+5.58s / +1.80s)은 크지만 **창의성으로 주장하면 안 되고 reference 필수**
- 우리 것으로 주장 가능한 부분 하나 : **break score O(1) precompute** — 원래의 storage-free 재계산은 candidate당 O(d²)라 2153-pin net에서 ~100s로 붕괴. precompute로 해결하면서 **스코어가 bit-identical**(트리 동일)임을 증명
- 스케줄링(오버랩)은 4위 항목으로 분리했음

#### 6위 — tree-center + leaf peeling

- 절감은 작지만 **"실패도 결과다" 서사의 주인공**
- 이중 BFS tree-center로 DAG depth 평균 **−23%** (max 45 → 28) → 그런데 **runtime은 안 줄어듦**
- 원인 규명 : 평균 depth가 아니라 **critical path**가 지배 + 호스트 측 center-find 비용이 이득을 상쇄
- 해결 : 이중 BFS → **leaf peeling**으로 호스트 비용 절감 → 순이득 전환, **기본 on**
- 현재 프로파일 : S1 eligible 126,006 / center-find 0.145s, S2 eligible 81,968 / 0.058s
